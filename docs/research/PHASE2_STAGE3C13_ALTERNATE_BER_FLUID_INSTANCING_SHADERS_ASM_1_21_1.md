## 2/4 — lifecycle, algorithm and collision of coordinate spaces

1. **Build/bake:** resource loading/NeoForge geometry loaders → BakedModel; `ModelData` often acquired from dynamic BE during chunk compilation. On a block/entity/model reload, preserve model selection and invalidate oriented-view caches appropriately. NeoForge RenderType and vertex material data must remain unchanged.
2. **Chunk rebuild:** block/fluids can have distinct render pipeline paths. A BakedModel-wrapper interception cannot apply to `IClientFluidTypeExtensions.renderFluid` or custom raw emitted vertices. Avoid patching every `VertexConsumer.addVertex`: it also draws vanilla/world-space geometry, item GUIs, foreign fake Levels and mod content.
3. **Dynamic BER frame:** dispatch binds BE and requested render buffers/light. A rigid-local BER may receive an opt-in `PlanetRenderTransform.applyAroundBlockCenter`; screen-facing labels, beams, world-space connections and portals must keep their own coordinate contracts. The `BedRendererGravityMixin` already wraps HEAD/RETURN Bed render only: **do not infer that this is a universal solution**. Snapshot BE Level/pos/frame consistently at entry to avoid asymmetrical push/pop if underlying level/context changes.
4. **Third-party fake contexts:** mod contraption Level or render-only Level must remain unmodified unless typed Planet provenance proves the object is a Planet spatial block. Previous C11 risk: `PlanetClientRenderFrame.stateFrameAt` may fallback to active ClientLevel for arbitrary non-Level `BlockGetter`; do not extend this heuristic into shader engines.
5. **Moving models:** physical instance position and frame interpolate separately. A block changing Planet faces near an edge can otherwise double-rotate, jump, or cast a shadow from the old matrix; renderer must own coherent current/previous transform data for motion vectors.
6. **Fluid render:** fluid flow graph and rendered surface are separately owned. Vanilla fluid renderer samples physical world-direction faces, color/alpha, shade, light and vector flow. Under local gravity the rendered free surface may need a local-frame geometric algorithm; NeoForge mod `renderFluid` is a **polymorphic mod-owned veto**, not a hook to bypass. Shadow/refraction/underwater fog shaders are a third distinct pipeline.
7. **Shaderpack render:** normals are world-orientation vectors after local model/PoseStack transformations, not local gravity vectors; special tangent-space normal maps and PBR material orientation also matter. Shadow maps are rendered from the sun/moon shadow camera, not the player's gravity frame. Do not rewrite world sun or sky light globally. Keep physical world coordinates for shader inputs; use explicit opt-in local-gravity metadata only for shader effects *designed* to need it.

### Shader source verification and mod compatibility boundaries

- [Iris coordinate spaces](https://shaders.properties/current/how-to/coordinate_spaces/): model-space is not guaranteed to be a single coordinate convention; terrain core profile requires `vaPosition + chunkOffset`; world/player space use physical axes; shadow-space is a separate camera basis. Iris warns `cameraPosition` can rebase; do not assume `worldPos = cameraRelativePos + static origin` indefinitely.
- [Iris matrix uniforms](https://shaders.properties/current/reference/uniforms/matrices/), [normal attribute](https://shaders.properties/current/reference/attributes/gl_normal/): `gl_NormalMatrix`, `gbufferModelViewInverse`, `shadowModelView` etc. Normals must be transported **once** through the same geometry transform, then transformed to view/shadow frames by the renderer/shader.
- [Iris core-shader compatibility notes](https://github.com/IrisShaders/Iris/blob/26.1/docs/development/compatibility/core-shaders.md): two arbitrary independently authored shader programs cannot generally be merged. A separate shaderpack-compatible fallback is sometimes required.
- [Flywheel & Iris compatibility addon](https://github.com/leon-o/iris-flw-compat) and [NeoForge 1.21.1 version](https://modrinth.com/mod/iris-flw-compat/version/1.21.1%2B2.3.0-release): shaderpacks can disable Flywheel optimizations; the addon re-enables instancing by combining shaders, with version-sensitive compatibility. Its existence means a **third render state** (shaderpack + accelerated instances) beyond “shader off/on.” This is a *source comparator*, not proof any particular Create, Flywheel or Iris binary is loaded. Do not describe Oculus as the necessary 1.21.1 NeoForge stack; Iris directly supports NeoForge 1.21.1.

### Root-cause diagnosis for reported odd side-face shadows

Before any fix, compare four renders of **the same physical scene**, camera pose and physical time/weather: vanilla graphics with AO off/on, Iris with **no shaderpack**, Iris with a shaderpack, and Flywheel instancing mode changed where compatible. Examine **three layers separately**: (1) actual vertex position + world normal and per-vertex AO brightness; (2) shadow-pass position/normals and front/back face culling; (3) shaderpack material/normal mapping and postprocessing. If (1) differs, debug Planet baked quad or BER transforms. If only (2) differs, debug alternate shadow geometry/instancing matrix. If only (3) differs, debug material texture/tangent orientation and shader conventions. Odd side shadow is still **unreproduced in a controlled test**, not diagnosed as a concrete defect in one class.

## 3/4 — deepest safe adapter, mod extension and coordinate contract

| Classification | Boundary | Rule |
| --- | --- | --- |
| **PHYSICAL_DO_NOT_TOUCH** | world `BlockPos`, camera/world XYZ, lightmap, sky direction, GPU view/shadow projections, `BlockAndTintGetter` physical positions, ordinary `VertexConsumer` and GPU draw for non-Planet objects | No global Y-to-local-UP transform or global vertices interception |
| **SHARED_SAFE** | position-provenanced original `BakedModel` wrapper; unchanged `ModelData`, render types, tint, NeoForge extension events; geometric conversion of emitted quads and packed normals | Reuse C11/C12 boundary when the *actual* render path passes through standard tessellator |
| **OPT_IN_ALGORITHM** | typed `PlanetRenderFrameContext` containing authoritative Level/provenance, physical BlockPos, chart/face and semantic frame, owner kind (BAKED/BER/FLUID/INSTANCE), render pass (MAIN/SHADOW/ITEM), normal/pose transform policy | Versioned thin renderer entry adapter performs transform ONCE at an owned semantic boundary; for rigid-local BER frame around block center; for mod fluid GPU emitter only when explicitly adapted |
| **MOD_INDEPENDENT** | arbitrary BER, custom item renderer, dynamic fluid callback, Flywheel/Sodium/Embeddium mesh engine, Iris/OptiFine shaderpack and third-party native shader programs | No assumed inherited vanilla method; identify loaded owner, compatibility API and fallbacks, prefer common engine extension points over named-block patches |
| **CLIENT_RENDER** | geometry normals, AO, shadow pass, PBR tangent basis, moving instance transforms, camera, render reload/invalidations and draw sorting | Phase 3 / Phase 10 runtime responsibility; test on real client with mod versions pinned |

**Why not deeper:** globally intercepting draw calls, `PoseStack`, all `VertexConsumer`, shader uniforms, or sunlight would double-transform external/world/camera-space draw data and destroy render-context isolation. **Why not shallower:** patching Bed or every vanilla BER misses arbitrary third-party BERs, custom fluid vertices, model loaders and GPU instances. A typed provenance contract for each algorithm family is the lowest SAFE shared boundary; not a magical one-hook solution.

**Version-portability:** semantics (`PlanetGravityFrame`, canonical->physical basis, chart/position provenance) should be version-independent. Minecraft/NeoForge-specific dispatch/selectors and shader- or engine-specific API adapters belong to versioned integration modules with explicit ABI tests and feature/capability probing. Shaderpack interfaces are optional client-only dependencies, never mandatory server class loading.
