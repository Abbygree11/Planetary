## Actual vanilla source ownership (32.1)

`BellBlock extends BaseEntityBlock`, **NOT** `FaceAttachedHorizontalDirectionalBlock`; uses that class's static `canAttach(LevelReader, BlockPos, Direction)`. Its `FACING` is `HorizontalDirectionalBlock.FACING` with only four original world-horizontal values in this implementation; `ATTACHMENT` is `BellAttachType.{FLOOR,CEILING,SINGLE_WALL,DOUBLE_WALL}`; `POWERED` boolean. Bell is not a generic arbitrary six-way `FACING` block, even on physical side faces. Its four attachments may be mapped from a canonical local player action **only if** produced state stays within the exact legal schema.

`BlockItem.useOn → place → getPlacementState → BellBlock.getStateForPlacement(BlockPlaceContext) → BlockState.canSurvive → Level.setBlock → BlockItem.updateBlockStateFromTag/BLOCK_STATE → update BE components/setPlacedBy`. Vanilla placement tries clicked vertical physical side first, `CEILING` on physical DOWN or `FLOOR` on UP, using `context.getHorizontalDirection()`; a lateral clicked face checks both supports on the *physical* chosen X or Z axis for `DOUBLE_WALL`, otherwise `SINGLE_WALL` with facing opposite click. Failed wall support attempts FLOOR via physical `below()`, then CEILING. This fallback is a **separate algorithm branch**, not a general `FACE` property author.

`BellBlock.canSurvive` maps `getConnectedDirection(state).getOpposite()` to support side: floor→DOWN; ceiling→UP, with `Block.canSupportCenter(pos.above(), DOWN)`; wall→state `FACING`, using the physically indexed neighbor + `FaceAttachedHorizontalDirectionalBlock.canAttach` / `isFaceSturdy`. `updateShape` is a separate override: loss of the principal support removes non-DOUBLE_WALL; wall-axis changes can convert DOUBLE→SINGLE and reverse FACING, or SINGLE→DOUBLE as the opposite support is restored. Do not implement this as generic `FaceAttachedHorizontalDirectionalBlock.updateShape`: BellBlock does NOT inherit it.

Other author/reader paths:
- `neighborChanged` consumes world redstone `hasNeighborSignal`, switches POWERED, and rings on rising power. **Phase7A** must own signal-side semantics; Phase2 only attachment and state.
- `useWithoutItem` and `onProjectileHit` call `onHit` → `isProperHit` (rejects world-Y impact normals; uses hit height `hitLocation.y - blockPos.y <= 0.8124F`, tests hit axis against FACING depending on attachment). This MUST be transformed through actual block-hit **local face and local height** on tilted faces; physical ray hit remains true world-space.
- `onExplosionHit` may ring from a null direction; `attemptToRing` on server falls back to FACING if direction absent, calls BE.onHit, plays sound and emits GameEvent; avoid double-rings and client-side ghost effects.
- `rotate/mirror` rotates only legal horizontal FACING; `getCollisionShape/getShape` have custom attachment-specific physical VoxelShape; `getRenderShape=MODEL` renders static support separately from animated bell body (**Phase3**).
- `newBlockEntity` instantiates `BellBlockEntity`; `getTicker` dispatches `clientTick` or `serverTick` for registered `BlockEntityType.BELL`; a custom BE type is NOT automatically covered.

`BellBlockEntity.onHit(Direction)` writes `clickDirection`, resets animation ticks and emits physical `Level.blockEvent(pos, block,1,dir.get3DDataValue())`; `triggerEvent(1,...)` decodes it, starts shake and refreshes nearby entity cache. Renderer animates `bellBody.xRot/zRot` for N/S/E/W physical directions. BE's 48-block physical AABB, 32-block hearing and raider checks, 50-tick shake, resonance/reveal logic are actual volumetric/server timing; **do not rotate the AABB or corrupt the packet's Direction serialization to fix visual motion**. Client resonation particles currently compute XZ offsets with world Y constant: **Phase3 particle emitter**, NOT Bell placement. Server raider glow/HEARD_BELL_TIME crosses Phase7/AI and must remain vanilla-equivalent.
