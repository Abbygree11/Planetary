## Source dispatcher and whole author graph (not only blocks)

`BlockItem.useOn → place → getPlacementState → PistonBaseBlock.getStateForPlacement` picks `BlockPlaceContext.getNearestLookingDirection().getOpposite()` (6 legal physical axes) with `extended=false`. After late item BLOCK_STATE components/BE NBT and `setPlacedBy`, own `onPlace` and `neighborChanged` call `checkIfExtend`. Redstone `getNeighborSignal` checks five non-front direct adjacent physical positions, downward self query and **quasi-connectivity at physical pos.above()** with five non-DOWN neighbors; this isn't "all six directions in the source local chart" by default. Client hit/player gaze semantically local on rotated gravity only at typed explicit placement boundary (Phase2); queried redstone side and QC author belong Phase7A.

`checkIfExtend → blockEvent(type 0 extend/1 or 2 retract) → triggerEvent (re-check power) → PistonStructureResolver.resolve → PistonBaseBlock.moveBlocks` is the authoritative vanilla state transition. Block event encodes `Direction.get3DDataValue` (physical identity). Extension creates moving PISTON_HEAD at adjacent physical position and per-moved-block MOVING_PISTON placeholder + `PistonMovingBlockEntity` containing `movedState`, `direction`, `extending`, `sourcePiston`, tick progress. Sticky retraction tests physical two-ahead block and `PushReaction.NORMAL`; finalTick of already moving head can be forced on event. Do NOT rotate event ID as if one global face-relative enum.

`PistonStructureResolver` physically starts `pos.relative(facing)` on extension and `pos.relative(facing,2)` with opposite push on retraction; `addBlockLine` collects forward/reverse and colliding overlap, `addBranchingBlocks` checks **four physical perpendicular directions**, not universal local UP, with invariant `MAX_PUSH_DEPTH=12` (total moved block budget, no accidental per-branch reset). `PistonBaseBlock.isPushable` applies actual physical build height/worldborder constraints, unbreakable and specific unpushable blocks, hardness -1, `PushReaction.{BLOCK,DESTROY,PUSH_ONLY}`, no moving block entities, unextended piston exceptions. Source physical level coords are stable even on side/floor gravity charts. Resolver action is real physical block displacement; merely rotating `FACING` on edges cannot turn a 12-block physical line into a seam-transported curved path without a separate graph+state-motion transaction.

`moveBlocks` calls `dropResources`/physical destroy hook for DESTROY reactions, writes target MOVING_PISTON placeholders and BE, removes sources, updates shape neighbors and notifications, not ordinary BlockItem placement. `MovingPistonBlock` is BE-driven, created synthetically by piston; `PistonHeadBlock.canSurvive` matches corresponding extended base behind it, own `updateShape`/neighbor, no ITEM creators. `PistonMovingBlockEntity.tick` advances 0.5 progress per server tick until finalization and re-evaluates neighbour shapes for final state; late WATERLOGGED cleanup and `updateOrDestroy` are NOT equivalent to generic place. BE `getXOff/getYOff/getZOff` and model/BER are render-phase consumers, serialized `movedState` is nested state with FACING and other properties needing a documented transform policy if seam transport is eventually implemented.

`PistonMovingBlockEntity.moveCollidedEntities` sweeps moving VoxelShape/AABB, collides and `Entity.move(MoverType.PISTON,PHYSICAL_VEC3)`, sets physical deltaMovement on moved slime; `moveStuckEntities` for honey is **gated by physical horizontal movement axis** and uses **WORLD Y top AABB**, entity `onGround/isSupportedBy` and XZ footprint. So neither side-face honey transport nor gravity-aligned falling bounce is solved by just rotating the block shape. `SlimeBlock.fallOn/updateEntityAfterFallOn/stepOn` affects physical Y bounce, `HoneyBlock.fallOn/entityInside/isSlidingDown/doSlideMovement` uses Y gravity: separate Phase7 entity local-gravity adapter, Phase3 slide particles/render, and Phase7A piston swept collision. Preserve physical Vec3/AABB for physics and mod APIs; canonical "support" must be expressed as typed gravity frame input, never reinterpret global Y silently.

## Critical NeoForge 1.21.1 comparative patch/extension contracts (target release ASM still OPEN)

- Source branch `PistonStructureResolver.java.patch` replaces vanilla hardcoded `isSticky(slime/honey)` with **`BlockState.isStickyBlock()`** and two-sided `state1.canStickTo(state2) && state2.canStickTo(state1)` in both backline and branch scans. `IBlockExtension` (via BlockState extension forwarding) supplies mod-defined stickiness and adhesion. **Never implement custom blanket hardcoded slime/honey for Planet, never drop symmetric checks.** A mod variant need not inherit `SlimeBlock` or `HoneyBlock` to stick.
- `PistonBaseBlock.java.patch` injects `EventHooks.onPistonMovePre` (cancellation on extend/retract), `onPistonMovePost`, `BlockState.onDestroyedByPushReaction(level,pos,physicalPushDirection,actualFluidState)`, plus a separate world/position aware `rotate` override that treats extended pistons specially. Do not bypass events/destroy hook when implementing graph; original phase2.3C exact ASM comparison separately required.
- `PistonMovingBlockEntity.java.patch` delegates slime-like moved entity acceleration to `movedState.isSlimeBlock()` rather than vanilla exact `Blocks.SLIME_BLOCK` ID. Not the same as `isStickyBlock` (slime behaviour != adhesive graphite/any sticky).
