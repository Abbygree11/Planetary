## 2/4 — complete lifecycle / bypass inventory and existing Planet runtime

**Scheduled and random clocks:** `ServerLevel.tickFluid` reads current FluidState and invokes dynamic FluidState.tick only if fluid identity still matches (2.3C-5). `FlowingFluid.tick` then computes source/flowing state, performs actual Level.setBlock and reschedules. `LiquidBlock.onPlace` and `neighborChanged` also independently schedule fluid ticks **unless** NeoForge FluidInteractionRegistry handled reaction. `SimpleWaterloggedBlock.placeLiquid` and `updateShape` schedule fluid ticks; waterlogging pick-up, buckets, commands, structures, worldgen features and mod fluid emitters can author state without executing a player placement callback. Source creation must invoke `EventHooks.canCreateFluidSource` per-neighbor to retain fluid type rules; do not prefilter using older WaterFluid-only gamerule. Vanilla and modded source conversion can be gated by FluidType and events.

**Planet-specific code reviewed:** `PlanetWorldAccess` has separate `PlanetTickScheduler<Fluid>` and canonical `getFluidState`, `setBlockState`, bridge `PlanetVanillaTickBridge` routes exact bound ServerLevel `LevelTicks<Fluid>` schedule/dedup/read. `LevelMixin.planetary$getFluidState` intercepts `getFluidState` at HEAD for encoded chart aliases; the implementation does **not** by itself replace `FlowingFluid.getFlow/getNewLiquid/getSpread/getSlopeDistance` planar XZ graph, world-Y source construction, per-face occlusion caching or waterlogging algorithm. No dedicated FlowingFluid simulation adapter Mixin observed in inspected production tree. Thus **possible source-level implementation gap**, not yet a gameplay reproduction. Other game acceptance limits: 2.3C-5 independent virtual fluid random tick section sampling and combined 65536+65536 scheduler cap, 2.3C-4 NeoForge neighbor event delivery, 2.3C-6 mod BE and fluid-handler capabilities persistence.

**FluidInteractionRegistry pitfall:** its later pinned code loops `LiquidBlock.POSSIBLE_FLOW_DIRECTIONS` and looks at `pos.relative(direction.getOpposite())` before invoking registered `FluidType` predicates. A Phase5 adapter changing *only* FlowingFluid would still leave a physical five-direction reaction scan at side/bottom Planet faces. Conversely indiscriminately rewriting `FluidInteractionRegistry.canInteract` globally breaks non-Planet fluids, fake Levels and external mod algorithms. On Planet, an explicit typed adjacency adapter must call mod registry interaction logic with correctly transported source and target positions exactly once.

**Shape/render:** `FlowingFluid.getShape/getHeight` and client `LiquidBlockRenderer` have separate +Y/Facing assumptions, and the entity consumes a **WORLD** flow vector. Do not confuse client falling/drip particles with authoritative server simulation. Existing `ClientLevelFluidDripGravityMixin` had a brittle redirect disabled by R3, must not re-enable ad hoc. Phase5 scene/client+Phase7 entity integration are separate.

**Environmental interactions:** bubble columns, cauldrons/dripstone, lava igniting mod blocks, fluid source conversion, waterlogged support, entity movement and NeoForge `IFluidHandler` (capability fluid storage) belong to distinct author/BE and physic paths. A pipe containing fluid as `FluidStack` is not automatically `FluidState` in a world cell; a mod tank/wire/pump may create fluid via direct Level writers. Bucket sound and vaporization are item+FluidType owned.

## 3/4 — deepest safe shared boundary / third-party compatibility

| Disposition | Mechanisms | Rule |
| --- | --- | --- |
| **PHYSICAL_DO_NOT_TOUCH** | BlockPos, Direction, world Level/FluidState APIs and default WORLD-space flow vector, actual collision VoxelShapes, real/foreign Level and worldgen chunks | Other mods, fake Levels, fluid tanks and vanilla non-Planet worlds expect physical XYZ |
| **SHARED_SAFE** | Original FluidState→Fluid dynamic dispatch, NeoForge EventHooks.canCreateFluidSource, FluidInteractionRegistry predicates, LiquidBlockContainer.placeLiquid, FluidType and BucketItem extension | Preserve all mod overrides with original state/type and callbacks |
| **OPT_IN_ALGORITHM** | Planet chart-aware FlowingFluid graph, local down/up/tangents, transported slope recursion and cache keys, local source count, interaction neighbor candidate enumeration and frame-specific collision shape | Only Planet owned/typed positions, explicit real physical source+target and source/target charts |
| **MOD_INDEPENDENT** | Custom Fluid subclasses, BaseFlowingFluid overrides, external block/machine/pipe fluid authors and `IFluidHandler`, independent bubble/dripstone/cauldron/structure and commands writers | Observe/call mod-defined APIs at boundaries; do not assume inheritance from vanilla FluidType or WaterFluid |
| **CLIENT_RENDER / ENTITY** | LiquidBlockRenderer mesh, drips, view, bucket hit UI, entity current/traction | Separate authoritative server from renderer/world Vec3 usage |

Proposed **future only** stable core `PlanetFluidEdge` built from existing `PlanetBlockStep`, recording canonical source/target `PlanetBlockPos`, requested local movement (DOWN/UP/tangent), physical crossing Direction and physical target, transported continuation direction and source/target frames. Additional typed `PlanetFluidFlowContext` tracks author `TICK/SPREAD/BUCKET/WATERLOG/REACTION/WORLDGEN/MOD`, `FluidState`, `FluidType`, `BlockState`, scheduling and cache chart keys. Thin version adapters own NeoForge/MC exact method targets. `PlanetFluidEdge` is **not implemented** in 2.3C-10.

**One layer deeper unsafe:** a blanket modification of `BlockPos.below`, `Direction.DOWN`, `FluidState.getFlow`, `Level.setBlock`, `FluidInteractionRegistry` or physical `getFluidState` rewrites unrelated mod/fake-world liquid behavior. **One layer shallower insufficient:** patching `LiquidBlock` or bucket alone never fixes actual FlowingFluid slope, source count, local gravity, occlusion cache, renderer nor modded FlowingFluid subclasses. Preserve mod polymorphism while adapting the explicit seam graph.
