## Exact algorithm and dispatch comparison

| Owner/mechanism | Vanilla Budding Amethyst / Cluster | **AE2 Certus** | **BuddingCrystals** |
|---|---|---|---|

| Java cluster inheritance | \`AmethystClusterBlock extends AmethystBlock\` | **\`CertusQuartzClusterBlock extends AEBaseBlock\`**, NOT \`AmethystClusterBlock\` | **\`CrystalSet.Builder\` directly registers four \`new AmethystClusterBlock(...)\` instances** using \`BudSet\`, plus budding source subclass |
| Growth trigger | \`randomTick\`, 1/5 gate | own \`randomTick\`, **1/5** gate | own \`randomTick\`, **\`1/growthChance\`** configurable per crystal set, not necessarily 1/5. Example \`BCContent.SALT.growthChance(1)\` |

| Creation / aging | AIR or *source WATER with amount8* → small → medium → large → cluster, only if previous bud \`FACING==dir\` | **same steps/conditions** using independent AEBlocks small/medium/large/cluster | **same four steps/conditions** from data/configured \`BudSet\` |

**Consequence:** A Planetary Mixin that only targets \`AmethystClusterBlock\` will MISS AE2 \`CertusQuartzClusterBlock\` entirely, even though the same static property instances are referenced. A Mixin targeting \`BuddingAmethystBlock.randomTick\` may not handle AE2 (separate class) and can be bypassed by BuddingCrystals **overridden randomTick**. For BuddingCrystals the concrete cluster blocks are **vanilla AmethystClusterBlock**; existing vanilla class support hooks can be shared, while the budding tick override remains a separate dispatch path. If Planetary changes generic \`BlockPos.relative\`, it risks corrupting *actual physical 3D growth neighbor searches*; if it only patches custom vanilla class orientation, independent AE2 \`getStateForPlacement\`/support and shapes remain uncorrected. This demonstrates **same semantics ≠ same Java declaring owner** and **same static BlockStateProperties reference ≠ shared method implementation**.

## Safe shared integration strategy (research only, no code)

1. **Physical adjacency and growth** remain six actual XYZ face-adjacent BlockPos with exact real target FluidState and one stored state. Do not “chart-hop” every tick probe at cube seam or invent 6 physical aliases. AE2 degradation writes the physical *parent source cell* separately from a crystal at target.
2. **Generic semantic support and placement** is a distinct source/target canonical Planet frame / clicked-hit conversion mechanism. Choose a stable owner boundary (\`BlockPlaceContext\` semantic orientation with opt-in provenance; target \`BlockState.isFaceSturdy\` or explicit source-local attachment policy), not wide/global Direction mutation. Physical rendering VoxelShapes remain real and must be adapted in Phase3. Source-local up applied to a world outer surface must never overwrite the physical 6-direction growth graph.
3. **Source-level structural grouping**: vanilla \`AmethystClusterBlock\` (already reviewed 4/1060 IDs), AE2 \`CertusQuartzClusterBlock\` independent declaring methods, BuddingCrystals source mod subclass with separate randomTick. Need **three distinct acceptance probes** for actual two mods loaded: block placed all 6 face interiors, edge/corner, support removal, updateShape, fluid and 0..3 bud aging. For AE2 additionally wear transitions and Growth Accelerator optional mechanics; BuddingCrystals growthChance differences (e.g. salt) and actual instantiated BudSet states.
4. **Compat architecture**: baseline registered vanilla 241 classes / 1060 IDs census is NEVER a census of modded BLOCK IDs. DO NOT add AE2 or BuddingCrystals Java classes to vanilla original ledger nor mark modded ASM/compat PASS. Maintain a separate modded class/registry capability matrix with **confirmed source SHA**, Minecraft/NeoForge versions and actual loaded runtime class/accepted callback proof. Consider an optional mod-specific adapter only after shared mechanism/dispatch inspection and actual incompatibility is proven.
