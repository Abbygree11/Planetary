### A. Lectern — book component and page menu vs physical redstone/scheduled state

`LecternBlock.getStateForPlacement` writes 4-horizontal `FACING` plus `HAS_BOOK` based on BlockPlaceContext and privileged BE data; standard `BlockItem` may apply actual BlockEntity components after placement and bypass simple vanilla state setting. `LecternBlockEntity` owns actual `ItemStack book`, page/pageCount, 1-slot read-only `Container` for menu plus `ContainerData page`, `setPage` clamp; `WrittenBookItem.resolveBookComponents` is a separate data/provenance/permission dependency: retain original player permissions and book content, never synthesize component resolution. `LecternBlock.tryPlaceBook/placeBook` from ItemTags.LECTERN_BOOKS consumes 1 real stack, BE`setBook`, `LecternBlock.resetBookState` directly `Level.setBlock(HAS_BOOK/POWERED)`, updates physical `pos.below()`. Actual page-change callback `signalPageChange` drives real POWERED pulse 15 for **2 scheduled ticks**, physical direct redstone signal only `getDirectSignal(direction==Direction.UP)`, BE page-comparator `floor(page/(pages-1)*14)+1` (with one-page special case); do not local-rotate redstone callback direction for unknown observers. Removal `popBook` creates real ItemEntity `x/z +0.25*FACING, y+1`, clears BE contents, physical neighbor notifier and drop must stay single occurrence; CLIENT page animation vs SERVER item output separate. Both `useItemOn` and `useWithoutItem` dispatch are active.

### B. Jukebox — record component ItemStack/BE, song lifecycle, physical sound, sided container

`JukeboxBlock` has no FACING; `HAS_RECORD` boolean and `JukeboxBlockEntity` store `RecordItem` original NBT + component `DataComponents.JUKEBOX_PLAYABLE`. `setPlacedBy` overrides original setPlacedBy and detects original `BLOCK_ENTITY_DATA.RecordItem`, directly updating HAS_RECORD. `JukeboxPlayable.tryInsertIntoJukebox` (item click) vs empty-hand BE `popOutTheItem` (physical spawn at `pos + (0.5,1.01,0.5)` + jitter) and `onRemove` all produce item/song state changes; no duplicate records. BE `setTheItem` toggles `JukeboxSongPlayer.play/stop`; ticker only when HAS_RECORD; `getComparatorOutput` based on original `JukeboxSong.comparatorOutput`, physical `getSignal` level15 only while actually playing, async music sound/network tied to real dimension+BlockPos. BE `getMaxStackSize=1`, `canPlaceItem` checks JUKEBOX_PLAYABLE and emptiness, `canTakeItem` has original other-container-empty condition. `setPlacedBy`, player click, dispenser/hopper, mod custom playable component and load/tick are **independent paths**; generic block orientation mapping does not adapt record ejection or audio emitter.

### C. NoteBlock — physical ABOVE and BELOW instrument provider, note range, event and sound

`NoteBlock` does not use `BlockEntity`: legal `INSTRUMENT` 23 enum types, `NOTE=0..24`, `POWERED`. `getStateForPlacement→setInstrument(LevelAccessor, BlockPos,state)` queries actual **`pos.above().BlockState.instrument()`** for top special instrument; otherwise reads **`pos.below().BlockState.instrument()`** (fallback HARP for certain top-only instruments). `updateShape` only recalculates when callback original **physical Direction.Axis.Y**, `neighborChanged` checks original `hasNeighborSignal` and on rising edge calls `playNote` (blockEvent + GameEvent.NOTE_BLOCK_PLAY) and sets POWERED; `useWithoutItem` cycles note and plays, `attack` plays without tuning. `useItemOn` special case `ItemTags.NOTE_BLOCK_TOP_INSTRUMENTS` clicked physical `Direction.UP` skips default interaction (placement of head etc). `playNote` requires top air unless instrument `worksAboveNoteBlock`; `triggerEvent` plays sound with pitch `2^((note-12)/12)`, emits NOTE particle at physical **y+1.2** and reads custom skull note sound from real `pos.above()` SkullBlockEntity. Critical algorithm semantics are **instrument-provider top/bottom**, **clicked top face**, **redstone neighbor**, **visual particle local normal**, **audio real emitter** — four different provenance types. Generic world-Y rewrite/side conversion for all mod sound blocks would break unknown physical neighbor sound sources. Planet canonical top/bottom can be opted-in by *Noteblock algorithm owner* and only with valid registered instrument enum; actual sound emission and NoteBlock sound events must retain real BlockPos.

### E. Smithing/Stonecutter/Grindstone — work happens in *menu*, not block ticking inventory

- `SmithingTableBlock extends CraftingTableBlock`, no own state properties and **no persistent BE**; `getMenuProvider/useWithoutItem` returns `SmithingMenu(ContainerLevelAccess.create(level,pos))`. `SmithingMenu extends ItemCombinerMenu`, reads real `RecipeType.SMITHING` with template/base/addition 3 inputs and result; `createResult/onTake` consume one each, preserve exact input ItemStack components, result recipe and advancement/event, `stillValid` checks real block. SERVER authority, client GUI and no imaginary BE or WorldlyContainer. Fallback `CraftingTableBlock` menu path is not the active smithing recipe algorithm.
- `StonecutterBlock extends Block`, original four-horizontal FACING placement, no persistent BE; `StonecutterMenu` holds ephemeral 1-input, choice list `RecipeType.STONECUTTING`, result slot, selected recipe index, shift-click/onTake item consume/award/stats, real block validation and `ContainerLevelAccess`. Direction changes the model, **not** recipe output vector or physical inventory side.
- `GrindstoneBlock extends FaceAttachedHorizontalDirectionalBlock`, original `FACE` three enum and `FACING` four horizontal = 12 states; exact original placement owner is parent `FaceAttachedHorizontalDirectionalBlock`, which iterates `BlockPlaceContext.getNearestLookingDirections`, computes candidate floor/ceiling/wall with actual `getConnectedDirection/canAttach/isFaceSturdy`, then `GrindstoneBlock.canSurvive` OVERRIDE **returns true**. Its original `updateShape` owner is parent and checks support on original physical neighbor callbacks, but canSurvive returns true; do not substitute another torch/button support predicate. Grindstone has distinct `getShape` and `getCollisionShape` physical AABBs per FACE+FACING, no persistent BE; `GrindstoneMenu` ephemeral two inputs and result, two-item repair/disenchant, preserve curse/enchants and components, actual XP spawned at true `Vec3.atCenterOf(realPos)` when output taken, player result/save semantics. Neither recipe menu nor XP logic is adapted by BlockItem alone.
