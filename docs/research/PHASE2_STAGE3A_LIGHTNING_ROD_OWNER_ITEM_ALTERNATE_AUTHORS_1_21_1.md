## 2. Complete concrete source dispatch — geometry, state, lightning and ticks

[`Blocks.LIGHTNING_ROD`](https://github.com/hackersense/OptiFine-Source/blob/b77c5c6995874f6cf2755bc5234428906b337b75/1.21.1/net/minecraft/world/level/block/Blocks.java#L7050-L7064) registers `new LightningRodBlock`, NOT the already-reviewed EndRodBlock. [`DirectionalBlock`](https://github.com/hackersense/OptiFine-Source/blob/b77c5c6995874f6cf2755bc5234428906b337b75/1.21.1/net/minecraft/world/level/block/DirectionalBlock.java#L8-L18) owns `FACING=BlockStateProperties.FACING` vocabulary (6 legal directions); [`RodBlock`](https://github.com/hackersense/OptiFine-Source/blob/b77c5c6995874f6cf2755bc5234428906b337b75/1.21.1/net/minecraft/world/level/block/RodBlock.java#L12-L62) owns actual **physical** X/Y/Z-aligned slender VoxelShapes, `rotate/mirror` and non-pathfindability. [`LightningRodBlock`](https://github.com/hackersense/OptiFine-Source/blob/b77c5c6995874f6cf2755bc5234428906b337b75/1.21.1/net/minecraft/world/level/block/LightningRodBlock.java#L24-L154) extends RodBlock, implements `SimpleWaterloggedBlock`; default FACING=UP, POWERED=false, WATERLOGGED=false. Its `getStateForPlacement` uses `BlockPlaceContext.getClickedFace()` directly, and actual target fluid `== Fluids.WATER` for WATERLOGGED; NOT player look, local-UP, or assumed bottom-only rod orientation. `canSurvive` inherited from BlockBehaviour, not a bespoke adjacent support gate. Direct ordinary world/block placement has no custom `setPlacedBy`, BE or `randomTick`.

Concrete method algorithm inventory:
- `updateShape` schedules WATER fluid tick if WATERLOGGED, then `super.updateShape`. `getFluidState` yields Water source for WATERLOGGED, otherwise inherited fluid. Waterlogging/fill/removal behavior belongs Phase 5; no direct evidence a current Planet adapter drives it.
- `getSignal` returns **15** to ordinary signal query when POWERED, **0** otherwise; `getDirectSignal` returns **15** only if POWERED **and `FACING == queried Direction`**, not on all faces. `isSignalSource` always true. The queried Direction is supplied by actual Level/BlockState redstone API: source canonical direction vs physical world direction **must be audited at the caller before a future Mixin**, not assumed automatically local.
- `onLightningStrike` sets this block `POWERED=true` with `Level.setBlock(...,3)`, calls `updateNeighbours` at `rodPos.relative(FACING.getOpposite())` and schedules **8 block ticks**, emits level event **3002** whose data is `FACING.getAxis().ordinal()`. `tick` resets POWERED=false and updates same neighbor; `onRemove` updates neighbors if a POWERED rod is actually replaced by different block; `onPlace` resets incoming POWERED state if replacing another block and there's no existing scheduled block tick. Other source writer scenarios that set POWERED without scheduler must be tested separately: don't assume “POWERED always lasts exactly 8 ticks” for arbitrary commands/templates/item components.
- `animateTick` is client-only thundering gate with world-Y `pos.getY()==getHeight(WORLD_SURFACE,x,z)-1`, game-time/random checks, electric sparks spawned along `FACING.getAxis()`. **Rendering and surface detection** depend on vanilla world XYZ separately from event/redstone logic. No lightning bolt automatically spawned by animateTick.
- `codec` simpleCodec, property definition FACING/POWERED/WATERLOGGED, `onPlace/onRemove`, `tick`, `getStateForPlacement`, `updateShape/getFluidState`, `getSignal/getDirectSignal`, `isSignalSource` and `animateTick` all audited source. No own `neighborChanged` override, no own scheduled randomTick, no BE event listener. Core local rod geometry/shape is owned by RodBlock; splitting by concrete class without following that base would misclassify behavior.

The block's `POWERED` change, delayed tick and neighbor output are independent of Item.place. LightningBolt also has independent fire placement; do not attribute it to rod state placement.
