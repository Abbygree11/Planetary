# Stage3A-31 — complete MECHANISM taxonomy of visually directional pattern/texture owners, vanilla + third-party, not just glazed terracotta

**Research scope is ALL mechanisms that can visually orient a block**, not only `GlazedTerracottaBlock`. Based on original NeoForge21.1.215 registry 1060 IDs/241 Java concrete classes and pinned original available Chipped + Rechiseled source/assets. The registrar has **398** original block IDs possessing at least one `facing/axis/orientation/rotation/half/face/attachment/shape` candidate property in this separate 8-property set; that is a **mechanical search index**, NOT '398 patterned blocks', not full visual coverage. The other662 IDs may still carry asymmetric static pixels, per-face tile models, material/map color changes, random model rotations, seamless texel patterns or CTM. These two groups are NOT evidence of a 398/1060 or 1060/1060 visual acceptance.

## Exact shared PLANET implementation situation as of Stage31

- `src/main/java/dev/planetary/mixin/ModelBlockRendererPlanetMixin.java` targets only a specific `ModelBlockRenderer.tesselateBlock` descriptor and substitutes a `BakedModel` with `PlanetBakedModelRotation.orientForBlock`. It operates on **STATIC baked models**. It is not a validated catch-all for BER, custom pipelines, mod atlas/CTM render overrides, or worldgen and placement.
- `PlanetBakedModelRotation` rotates Quad geometry/normals/side selection based on block canonical face; caches model by `BakedModel+PlanetFace`, and has special seam logic only for `SpreadingSnowyDirtBlock` (not 'all patterned surfaces'). Verify `RenderType`, `ModelData`, dynamic/unlisted data, baked quad procedural selections, UV transformation and culling per mod.
- `PlanetBlockStateFrame`, `PlanetBakedModelRotation` and `PlanetBlockShapeRuntime` operate on different domains: world semantic state, client quads and server physical collision respectively. Do not rotate a vanilla `FACING` twice just because JSON blockstate already applied 90°. The *visual motif orientation* must agree with a real clicked semantic state and source/target chart.
- A patterned block with `NO FACING` remains a legitimate candidate for **static model rotation** but no expectation that two face charts can always tile its texture continuously. Some asymmetric 2D face art is authored relative to a nonrotatable world coordinate. Per-pattern expected continuity must be specified, not guessed.
- **Source-only audit does NOT equal full asset coverage**: vanilla model JSON and actual loaded mods with their shader/texture-pack variations still need exact-pinned source asset and live game render tests. Avoid claiming all modded visually patterned blocks covered from a nine-class owner scan.

## Whole-family acceptance gates (do not mark before runtime proof)

Visual + semantic tests must cover original BlockItem/GameMasterBlockItem/other alternate writers, 6 Planet faces,12 seams,8 triple corners, 2×2 motif continuity and rotation winding, UVLOCK, mod graphics with/without FACING, side-specific textures/CTM/BER, neighbor chart provenance, exact source BlockPos vs physical target, server saved states and client model quads, vanilla noPlanet and fake-world passthrough. Unknown mod code remains physical by default. Any uncovered owner must be added to this matrix and assigned to Phase2 state / Phase3 render / Phase8 worldgen / Phase9 structure, rather than patched by single glazed-texture ID.
