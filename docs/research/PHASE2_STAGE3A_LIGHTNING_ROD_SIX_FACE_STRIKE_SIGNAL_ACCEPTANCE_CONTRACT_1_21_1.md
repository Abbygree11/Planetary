**Six actual canonical bases (from current `PlanetFace`):**

| Face | local UP → physical | local EAST → physical | local SOUTH → physical |
|---|---|---|---|
| POS_Y | +Y | +X | +Z |
| NEG_Y | −Y | +X | −Z |
| POS_X | +X | −Y | +Z |
| NEG_X | −X | +Y | +Z |
| POS_Z | +Z | +X | −Y |
| NEG_Z | −Z | −X | −Y |

For example, **POS_X** surface-local UP points **world +X**. A rod pointing locally UP must ultimately have an outward physical shaft along +X; its support and neighbor-update target lie one *physical* block world −X. Vanilla `FACING=UP` and vanilla world-Y spark check would instead mean +Y on this face unless explicitly adapted **at the correct owner**. The target's incoming query side may differ from the rod's own canonical local side across a seam; use neighbor query source+target frames, not blindly reuse the same enum.

## 2. Source-driven lifecycle, edge and corner invariants

- **Clicked face vs stored property vs physical geometry:** `BlockPlaceContext.getClickedFace()` is a real physical face; the `LightningRodBlock` implementation authors FACING directly. A proposed canonical-local property adapter must make the stored semantic FACING and world shaft compatible, and must not double-rotate an already physically oriented shape. The incoming clicked side and outgoing direct signal query side are **different API roles**, with different transforms (test both). `RodBlock.rotate/mirror` and `StructureTemplate` use state rotations independent of item placement.
- **Power source:** `onLightningStrike` writes POWERED=true then runs `updateNeighbours(pos.relative(FACING.getOpposite()))`, schedules **8 ticks**, and fires event 3002. Subsequent `tick` writes POWERED=false and notifies the matching neighbor. `getSignal` ignores direction and returns 15 while powered; `getDirectSignal` checks direction equality. **Do not globally rewrite Direction passed to `Level.getSignal/getDirectSignal`.** Resolve source canonical frame vs queried physical side at the adapter boundary with proof of the API's sign conventions.
- **No automatic 8-tick reset for arbitrary writers:** `onPlace` explicitly resets incoming POWERED=true when its previous block differs and no scheduled rod tick exists. Post-item `BLOCK_STATE`, `/setblock`, `/fill` and template/mirror rotation can trigger different write order and lifecycle, and must be tested rather than assumed stable. Replacing an already powered rod invokes `onRemove` neighbor propagation; same-block property changes should not be treated as removing rod.
- **LightningBolt physical strike position** and WeatheringCopper oxidation clearing behind the FACING-opposite rod are one graph. The copper walker deliberately visits random *physical* neighbors; it should not unknowingly teleport around Planet curvature with a traversal chart. LightningBolt fire spawn is separately owned and not a LightningRod state update. Weather target selection across physical +X/+Z/−Y exterior and storm precipitation coverage require separate Phase 8/9 evidence, not just lightning-rod facing adaptation.
- **Exact edges/corners:** 12 cube face-pair edges and 8 three-face corners should use one physical block and one canonical state. A traversal path can be stored only transiently; a newly placed or powered rod cannot become a duplicate entity/block/tick at the seam. Physical support target and direction to query its redstone response must be derived from a *unique* world neighbor; adjacent block may have a different local canonical face.
- **Water and particles:** actual water in the clicked target, waterlogged fluid-state ticks and neighboring liquid require Phase 5. `animateTick` world-Y weather-heightmap check is a visual/weather limit (Phases 3/8/9), not proof the rod fails to conduct lightning on a side face or proof it will spark after adapting FACING. Axis ordinal event 3002 must remain encoded consistently for clients and copper events (data -1), including no-Planet vanilla worlds.
- **No Planet field:** vanilla Overworld/Nether/End or test fake worlds must pass through unchanged. No global hit, state, neighbor-callback, weather, entity or coordinate monkeypatch. Explicit opt-in per mechanism.
