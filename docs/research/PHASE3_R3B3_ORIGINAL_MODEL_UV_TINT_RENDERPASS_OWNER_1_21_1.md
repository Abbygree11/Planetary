## 2/4 — Original UV, tint, multipart and render-pass ownership

The actual target compiled direct INVOKEs prove:

- `FaceBakery.bakeQuad` calls `ModelState.isUvLocked`, `FaceBakery.recomputeUVs`, `TextureAtlasSprite.uvShrinkRatio`, `makeVertices`, `calculateFacing` and `recalculateWinding`, and NeoForge-specific `ClientHooks.fillNormal`. In the same actual original method body it accesses `ExtraFaceData.color/blockLight/skyLight/ambientOcclusion` and applies `QuadTransformers.applyingColor` / `applyingLightmap`. The baked **geometry, normal, UV and mod light/color values already have individual authors**; do not make a blanket renderer overwrite every packed field when rotating physical axes.
- `FaceBakery.fillVertex` calls `BlockFaceUV.getU/getV` then `TextureAtlasSprite.getU/getV` and stores encoded per-vertex UV. The bake-time `ModelState.isUvLocked` flag is not a directive for Planetary to regenerate UVs on every runtime transform. Source-side model UV orientation and physical quad NORMAL rotation must be separated; an asymmetric arrow/wood-grain model may still expose an untested UV visual issue.
- `SimpleBakedModel.getQuads` retrieves per-side quads from its baked side map. `MultiPartBakedModel.getQuads` **resolves `MultipartModelData.resolve`**, reads child BakedModel RenderTypes and obtains child model quads. `WeightedBakedModel.getQuads` calls `WeightedRandom.getWeightedItem` and `RandomSource.nextLong`; child delegate occurs through a Java Optional/lambda path, so don't falsely interpret random variant selection as deterministic static-state quads or count only direct owner calls as full dynamic dispatch.
- `BakedModelWrapper` directly delegates both three-argument and five-argument `getQuads` to the **original model**, as well as `getModelData`, both `getRenderTypes` overloads, `getRenderPasses` and AO policy. These are generic NeoForge override points; generic Planet adapters should not replace their owner logic with custom per-block special cases.
- `BlockColors.getColor` has two direct callsites to registered `BlockColor.getColor`, preserving source block/position/biome and tint index semantics. `SectionCompiler.compile` calls `RenderChunkRegion.getModelData` and `BakedModel.getModelData/getRenderTypes` before render batches; that model-data source world and the renderer's physical local-frame resolution are distinct mechanisms.

Original NeoForge [`IQuadTransformer`](https://github.com/neoforged/NeoForge/blob/3cae64530de368936d4c07497d3f0a25e2f9ffec/src/main/java/net/neoforged/neoforge/client/model/IQuadTransformer.java) and [`QuadTransformers`](https://github.com/neoforged/NeoForge/blob/3cae64530de368936d4c07497d3f0a25e2f9ffec/src/main/java/net/neoforged/neoforge/client/model/QuadTransformers.java) published source, corroborated by the actual target compiled classfile inventory and the Planet six-face unit test: `IQuadTransformer` copies packed input quad vertices before transformation; `QuadTransformers.applying` transforms position and packed normal bytes, retaining UV0 and other original packed fields. Different NeoForge source commit is a **pinned source comparison**, not itself an assertion that the compiled target bytecode was dynamically executed. The CI-driven Planet fixture confirms the relevant actual loaded target transformation behavior for its synthetic normals/UV values. The original `BakedQuad` is never globally mutated by `rotateQuad`.

## 3/4 — Mod-aware bypasses and actual Planet wrapper integration

[35-row exact owner and acceptance matrix](PHASE3_R3B3_MODEL_UV_TINT_RENDER_PASS_OWNER_MATRIX_1_21_1.tsv) distinguishes ORIGINAL JVM, Planet SOURCE/JUnit, pinned released mod SOURCE and LOADED-GAME PENDING:

- `PlanetBakedModelRotation.OrientedModel` subclasses the original `BakedModelWrapper`. It maps the requested physical `Direction` to the corresponding canonical local side, delegates 5-argument `getQuads` with unchanged `ModelData`, `RenderType`, `RandomSource` and original model, then transforms the packed quad position/normal and output Direction. It inherits delegated model-data and RenderType methods. Existing `PlanetBakedModelRotationTest` already probes six-face coordinates/direction and a grass-specific seam; the new JUnit adds packed UV/light/color/tint/AO and ModelData/side assertions, not whole mod render acceptance.
- `PlanetBakedModelRotation.SurfaceSeamModel` still special-cases only `SpreadingSnowyDirtBlock` multi-face candidates. **Unknown generic missing side at a seam cannot safely be repaired by duplicating canonical UP faces on every block.** Need classify state author vs model got no quads vs face occlusion vs light/tint vs custom BER, using actual +Y/noPlanet comparisons.
- `PlanetClientRenderFrame` falls back from arbitrary non-`Level` getter to active `Minecraft.getInstance().level`. The original `RenderChunkRegion` stores its original producing `Level` and bounded `ModelData` snapshot (3R-2k/2l/2m). This is SOURCE-verified provenance risk, not reproduced client-world race; the 3E owner and task epoch gate remains pending.
- Original target `Block.shouldRenderFace` has a vanilla state-pair/direction ThreadLocal cache, while `PlanetBlockRenderCulling` uses a separate state-pair/two-local-side ThreadLocal cache. The absence of positions alone does **not** prove dynamic mod face cache wrong. Earlier 3R-2j verified moving piston **collision** shape, not face occlusion: avoid conflating them.
- Pinned released **AE2 NeoForge 19.2.18**: `GlassBakedModel` derives connected glass sides via two-way `BlockState.getAppearance` in `getModelData` and returns no directional `BakedQuad` for connected glass, independently from vanilla shouldRenderFace. `CableBusBakedModel` selects attached part models, keeps foreign `BlockAndTintGetter` in `FacadeModelData`, delegates nested `getQuads` and independently applies `QuadRotator`. `FacadeBlockAccess` may substitute a source block only if `this.pos == pos` **object identity**. No mod was loaded in Planet client in this packet. These model hooks may cause double rotation or no quad emission if globally altered; neither error is demonstrated at runtime.
- Pinned Create 6.0.10 `VirtualRenderWorld` owns virtual block and BE/ModelData state; a fake `Level` does not prove physical Planet origin. Its released build was compiled for NeoForge 21.1.219 vs project 21.1.215, so compatible loader and independent Create/Ponder render acceptance are still unknown. Flying renderer/BER/custom item/fluid routes belong to 3C/3D rather than being globally captured by a BakedQuad wrapper.
- Inventory/item model `getRenderPasses` and display transform remain distinct from world-position-local rotated blocks. Preserve their ownership; do not rotate GUI or held item model as a side effect of world face rotation without explicit requirements.
