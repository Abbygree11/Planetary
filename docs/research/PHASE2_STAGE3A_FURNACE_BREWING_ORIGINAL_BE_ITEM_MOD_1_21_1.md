### B1. Furnace superclass, THREE actual recipes and a shared BE tick

`AbstractFurnaceBlock.getStateForPlacement` sets horizontal FACING to `BlockPlaceContext.getHorizontalDirection().getOpposite()`; LIT default false. It owns `useWithoutItem` server menu; calls subclass `openContainer`, and its `onRemove` drops real `AbstractFurnaceBlockEntity` contents + calls `getRecipesToAwardAndPopExperience` + comparator updates only when actual old/new block types differ. It **does not implement** three different process engines; three subclasses return three BE types and run **`AbstractFurnaceBlockEntity.serverTick`**. `FurnaceBlockEntity` constructor `RecipeType.SMELTING`, `BlastFurnaceBlockEntity` `RecipeType.BLASTING`, `SmokerBlockEntity` `RecipeType.SMOKING`. `getTicker` selects exact BE type, correct server and client. Vanilla recipe types are data-driven, custom modded smelt/blast/smoke recipes may register to existing `RecipeType`; do not hardcode block whitelist/vanilla recipes. Their `animateTick` particles and facing offsets are independent CLIENT visual owners; do not alter server BE time/position while fixing particle drift. No legal vertical FACING state on any of the three; projecting canonical front to world UP/DOWN is invalid without a separate typed projection/renderer.

`AbstractFurnaceBlockEntity extends BaseContainerBlockEntity implements WorldlyContainer, RecipeCraftingHolder, StackedContentsCompatible`. Exactly THREE native slots: `0=input,1=fuel,2=output`. True physical sided slots: `getSlotsForFace(UP)=[0]`, `DOWN=[2,1]`, four horizontal sides `[1]`; `canPlaceItem(slot=2)=false`, `slot=1` accepts `isFuel` or specific bucket state; bottom fuel extraction slot1 permits only actual `WATER_BUCKET/BUCKET`, otherwise use normal output. **ALL of this is REAL PHYSICAL `Direction`**, not automatically `PlanetFace.localUp/down`. Vanilla `HopperBlockEntity.suckInItems` pulls from physical above using target DOWN, modded providers use capability sides: provenance and opt-in required per provider+caller, same rule as Stage23.

`AbstractFurnaceBlockEntity.serverTick` is an independent **server BE owner**: checks RecipeManager.CachedCheck of actual recipe type with `SingleRecipeInput`, remaining fuel `litTime/litDuration`, recipe `cookingProgress/cookingTotalTime`; consumes one valid fuel and handles crafting remaining item (e.g. bucket), finishes using `canBurn/burn` only if output matches components/max stack; records `recipesUsed` and drops/awards XP on real server; updates `AbstractFurnaceBlock.LIT` via direct **`Level.setBlock`**, bypassing `BlockItem.getStateForPlacement`. Input `setItem(0)` resets/changes recipe progress and recomputes cook time. NBT saves `BurnTime,CookTime,CookTimeTotal,RecipesUsed` and items; `getBurnDuration` fuel cache and recipe data are independent from block axis, should not be redirected. A rotated furnace with unchanged physical sides still processes normally but does not automatically match canonical local conveyor intent unless provider explicitly opts in.
