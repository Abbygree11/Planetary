## 1/4. Exact comparative vanilla entrypoint/dispatch (source inspected in this packet)

Pinned 1.21.1 comparative source base `hackersense/OptiFine-Source@b77c5c6995874f6cf2755bc5234428906b337b75` (NOT the verified patched 21.1.215 bytecode):

- [`UseOnContext`](https://github.com/hackersense/OptiFine-Source/blob/b77c5c6995874f6cf2755bc5234428906b337b75/1.21.1/net/minecraft/world/item/context/UseOnContext.java) exposes physical `BlockHitResult`, position, side, point, nullable player.
- [`BlockPlaceContext`](https://github.com/hackersense/OptiFine-Source/blob/b77c5c6995874f6cf2755bc5234428906b337b75/1.21.1/net/minecraft/world/item/context/BlockPlaceContext.java): constructor calculates `relativePos=hitPos.relative(hitFace)` physically; `replaceClicked=clickedState.canBeReplaced(context)`; `getClickedPos()` selects original hit or relative target; `at(context,pos,face)` builds a NEW physical hit and recomputes replacement. The direction reorder for a non-replacing target puts physical `getClickedFace().getOpposite()` first.
- [`BlockItem`](https://github.com/hackersense/OptiFine-Source/blob/b77c5c6995874f6cf2755bc5234428906b337b75/1.21.1/net/minecraft/world/item/BlockItem.java) `useOn` creates `BlockPlaceContext` and calls virtual `place`. `place` enforces enabled features, initial `canPlace`, virtual `updatePlacementContext` (nullable), virtual `getPlacementState`, virtual `placeBlock`, then re-fetches placed state and conditionally applies late `DataComponents.BLOCK_STATE`, `BLOCK_ENTITY_DATA` and BE components, calls `setPlacedBy`, advancement, sound, event and consumes stack. `getPlacementState` asks target Block's `getStateForPlacement` then `canPlace` (survival and physical collision). Base `placeBlock` writes `Level.setBlock(target,state,11)`.
- [`BlockItemStateProperties`](https://github.com/hackersense/OptiFine-Source/blob/b77c5c6995874f6cf2755bc5234428906b337b75/1.21.1/net/minecraft/world/item/component/BlockItemStateProperties.java) resolves property names from the ACTUAL chosen final block's StateDefinition; unknown properties / illegal values are ignored. A valid component may override initial FACING, AXIS or another property **after** `canPlace` and `placeBlock`, and the normal path does **not** rerun `getStateForPlacement`/`canSurvive` after this update. A global ItemStack property rewrite would destroy explicit user/mod orientation and command-authored data.
- [`DirectionalPlaceContext`](https://github.com/hackersense/OptiFine-Source/blob/b77c5c6995874f6cf2755bc5234428906b337b75/1.21.1/net/minecraft/world/item/context/DirectionalPlaceContext.java) uses NULL player and supplied synthetic direction, overrides `getClickedPos` / `canPlace` / nearest-direction order / horizontal direction / rotation. Its supplied direction must be treated as provenance-dependent, **not assumed player body-local**.
- [`DoubleHighBlockItem`](https://github.com/hackersense/OptiFine-Source/blob/b77c5c6995874f6cf2755bc5234428906b337b75/1.21.1/net/minecraft/world/item/DoubleHighBlockItem.java) overrides `placeBlock`, pre-clears a PHYSICAL `target.above()` cell with flags 27 before the base placement; this is not automatically the final upper half (e.g., `DoublePlantBlock` separately controls second-half creation). Requires source+target two-cell analysis.
- [`BedItem`](https://github.com/hackersense/OptiFine-Source/blob/b77c5c6995874f6cf2755bc5234428906b337b75/1.21.1/net/minecraft/world/item/BedItem.java) overrides `placeBlock` with flags 26. Head-half creation belongs to `BedBlock.setPlacedBy` and is not represented by a second BedItem `placeBlock` call.

**Critical ownership rule:** `Item.useOn()` -> `BlockItem.place()` is a common ingress, not a complete authorship barrier. Specialized `getPlacementState`, `updatePlacementContext`, `placeBlock`, non-BlockItem `Item.use()/useOn()`, block `useItemOn()`, worldgen, BE, commands and structure systems each can bypass a proposed generic orientation adapter.

## 2/4. Variant selection: standing/wall/ceiling, signs, banners, heads and mod siblings

[`StandingAndWallBlockItem`](https://github.com/hackersense/OptiFine-Source/blob/b77c5c6995874f6cf2755bc5234428906b337b75/1.21.1/net/minecraft/world/item/StandingAndWallBlockItem.java) overrides `getPlacementState`: eagerly obtains wall candidate, loops `context.getNearestLookingDirections()`, rejects one attachment direction, selects standing versus wall target Block depending on `attachmentDirection`, invokes EACH block's virtual `getStateForPlacement`, checks `canSurvive` through overridable `canPlace(LevelReader,BlockState,BlockPos)`, then unobstructed collision. `registerBlocks` maps one ITEM to both physical BLOCK instances. This is a **variant selector**, not only a blockstate orienter.

[`SignItem`](https://github.com/hackersense/OptiFine-Source/blob/b77c5c6995874f6cf2755bc5234428906b337b75/1.21.1/net/minecraft/world/item/SignItem.java) inherits that selector and adds `updateCustomBlockEntityTag` / text-edit UI hook. [`HangingSignItem`](https://github.com/hackersense/OptiFine-Source/blob/b77c5c6995874f6cf2755bc5234428906b337b75/1.21.1/net/minecraft/world/item/HangingSignItem.java) extends SignItem; constructs UP attachment and overrides `canPlace` with `WallHangingSignBlock.canPlace` in addition to base survival. `BannerItem`/`PlayerHeadItem`/coral variants share or specialize the item-to-multiple-block arrangement, but **this packet did not re-audit their own method bodies**; see prior 2.3A family studies, and keep exact registered ITEM-class coverage pending.

Prior exact original sign/banner registry ledger documents 76 BLOCK IDs but only **38 actual ITEMS**, so counting item registry IDs as one-to-one with block IDs is wrong. Prior 2.3A skull/coral studies document similar dual-block paths. The requested “wall-or-floor” behavior is an algorithmic selector; do **not** invent a common `WallOrFloorBlockItem` registered Java class without proof.

**Safe contract:** physical hit normal and candidate target stay unchanged. Convert **semantic intent** for *chosen target block's canonical frame*, preserving virtual `getStateForPlacement` and each candidate's distinct `canSurvive`/collision, selected block identity and registration. For edge/corner placement, the source clicked frame, player's body frame and target canonical state frame may differ.

## 3/4. Target rewriting, replacement, no-player and late authorship

[`ScaffoldingBlockItem`](https://github.com/hackersense/OptiFine-Source/blob/b77c5c6995874f6cf2755bc5234428906b337b75/1.21.1/net/minecraft/world/item/ScaffoldingBlockItem.java) overrides `updatePlacementContext`. If the chosen cell is not scaffolding, it rejects distance==7. Otherwise it selects direction from secondary use/inside/physical clicked face or player horizontal and WORLD UP, walks physical `MutableBlockPos` through scaffolding cells, checks physical world bounds and replaceability, creates `BlockPlaceContext.at` on chosen cell, or returns null. Horizontal traversal is bounded by 7 but the loop can also terminate at obstruction/build bounds. `mustSurvive()` is false; do not substitute ordinary survival rules.

This makes a **two-stage provenance**: initial click and final rewritten target. Compute any canonical-local placement intent only AFTER target rewriting. Never make `BlockPos.relative` globally chart-aware; it would break scaffolding searches, falling physics, foreign schematic Levels and many modded placement algorithms. A future explicit scaffolding stacking policy can opt into Planet local-UP while preserving physical candidate walks and original bounds/collision semantics; `ScaffoldingBlock` support/distance maintenance also requires independent audit.

No-player `DirectionalPlaceContext` must not be sent into helpers that read `player.getYRot()` or infer a body frame. This project's [`PlanetFrameApi.localNearestLookingDirections`](../../src/main/java/dev/planetary/api/PlanetFrameApi.java) returns empty for null players; current [`StandingAndWallBlockItemMixin`](../../src/main/java/dev/planetary/mixin/StandingAndWallBlockItemMixin.java) falls back to vanilla synthetic order. **Source-visible implementation exists**, but its transformed call-site in exact 21.1.215, item variants and full gameplay are UNVERIFIED. This fallback is correctness-preserving relative to vanilla behavior; it does NOT prove local-gravity correctness for dispenser/falling-block cases.

Late `DataComponents.BLOCK_STATE`, block-entity data, `setPlacedBy` and neighbor callbacks are separate writers. For FACING4, AXIS3, FACING6, ROTATION16, HALF, ATTACH_FACE and modded custom properties, treat values already stored in ItemStack as **explicit canonical-author intent by default**, not physical angles to reinterpret indiscriminately. Only a clearly identified physical-authored component producer may request typed conversion; the adaptation needs original target+final target+author provenance and property domain. Component parse legality belongs to the final selected Block's StateDefinition, including modded blocks.

**Deepest safe boundary reasoning:** One level shallower (per named block/item special patch) misses sibling items and inherited mod classes. One level deeper (changing generic physical `BlockPlaceContext.getClickedFace`, `Level.setBlock` or `BlockPos.relative`) corrupts geometry, worldgen, fake Level, mod graph algorithms and unspecialized callers. The eventual stable Planet semantic helper must receive typed **author intent + final physical target + final canonical state frame + source provenance**, then thin adapters at inspected item/BlockState author sites. No Java/Mixin modifications in this research packet.
