**Ignition engine and portal path.** `BaseFireBlock.getState(BlockGetter,BlockPos)` reads the **PHYSICAL below** supporting state and chooses **SOUL_FIRE** if `SoulFireBlock.canSurviveOnBlock` matches `BlockTags.SOUL_FIRE_BASE_BLOCKS`; otherwise delegates to FireBlock's physical placement algorithm. `BaseFireBlock.canBePlacedAt(Level,pos,player horizontal direction)` requires an actual AIR target plus survival OR portal-frame eligibility. `BaseFireBlock.isPortal` inspects surrounding real OBSIDIAN and `PortalShape.findEmptyPortalShape` orientation; `BaseFireBlock.onPlace` has dimension-scoped actual portal creation (overworld/nether), separate from ordinary flame support/renderer. Rotating all fire positions globally would corrupt portal coordinate structure and other mods.

**FireBlock topology is both physical and semantically vertical.** `FireBlock.getStateForPlacement` checks physical `pos.below()` and `isFaceSturdy(UP)`/flammable; if not supported from below, builds five physical directional booleans from `PipeBlock.PROPERTY_BY_DIRECTION` **excluding DOWN**. `getShape` is cached from `age=0` variant across those 5 booleans, default `DOWN_AABB`; `canSurvive` checks physical below sturdy UP OR any one of six physical neighbor flammables. `updateShape` reevaluates support and all directional booleans. These 5 bits are fire-face display/attachment topology, **NOT** a universal 6-axis FACING. No illegal DOWN property may be added to original state.

**FireBlock scheduled spread is not a generic 6-neighbor rotated graph.** `FireBlock.onPlace` schedules a fire tick; `FireBlock.tick` reschedules with **30+random nextInt(10)** and only runs spread when the **doFireTick** gamerule permits, with survival, source-infiniburn, age, rain-exposure and biome burnout gates. It samples six direct physical faces for burnout, then a bounded *asymmetric WORLD-Y volume* x/z offsets -1..1 and y offsets **-1..4**, with age/height/difficulty/probability, physical flammability tables, true neighboring BlockStates and additional weather gates; writes new fire BlockStates directly. That algorithm is a **separate typed heat/spread-volume POLICY**: rotating just `BlockPos.below` in placement will not rotate or preserve the fire-spread spatial sampling. `FireBlock.getIgniteOdds/getBurnOdds` uses hard-coded legacy block maps in comparable Java (WATERLOGGED block property short-circuit), `setFlammable` bootstrap list, and TNT callback on adjacent burn. Whether NeoForge 21.1.215 patches the flammability lookup to support custom `IBlockExtension` or events is a **separate ASM/patch REVIEW_PENDING** task; do not claim arbitrary mod burn odds are honored by vanilla Java code. `isNearRain` explicitly checks rain at physical target plus 4 horizontal offsets. No indefinite per-tick tree or graph should be inserted without profiling.

**SoulFireBlock survival and burn.** `canSurvive` matches only `SOUL_FIRE_BASE_BLOCKS` on **physical below** (e.g. soul soil family by tag); `updateShape` returns AIR if that support vanishes. `SoulFireBlock.canBurn=true` is a shared BaseFireBlock flag not evidence SoulFireBlock implements FireBlock's spreading age/scheduling. `BaseFireBlock.entityInside` sets/extends entity fire and delegates `damageSources().inFire()` with actual instance fireDamage **FireBlock 1 vs SoulFireBlock 2** from constructors (source-scale values; not proof of final armor/status damage), actual collision AABB and entity actual position. Game conditions and event hooks matter. Rendering/audio `BaseFireBlock.animateTick` accesses **physical below/west/east/north/south/above** and produces physical WORLD-Y smoke offsets independent from spread/server flame. `getShape` inherited BaseFireBlock for soul fire; PortalShape and entity contact are other owners.

**CampfireBlock is not a subclass of BaseFireBlock.** It is `BaseEntityBlock` + `SimpleWaterloggedBlock`, shares state family between plain and soul campfire, not soul fire. Source `CampfireBlock.getStateForPlacement` reads real target WATER `FluidState`, sets WATERLOGGED + LIT=!water, samples **below hay block** for SIGNAL_FIRE, and chooses `FACING=BlockPlaceContext.getHorizontalDirection()` (original HORIZONTAL_FACING 4 only). It does not rely on generic `BaseFireBlock.getState`. `updateShape` recomputes SIGNAL_FIRE only when PHYSICAL DOWN neighbor changes; when waterlogged, schedules true water fluid tick. This does **not** necessarily mean support logic should be reused from normal FireBlock: original Campfire.canSurvive is inherited BlockBehaviour, not a special block support method. `CampfireBlock.placeLiquid` dowses LIT, writes real WATERLOGGED+LIT false and schedules physical water; external flint-and-steel/fire-charge and on-fire projectile can relight only legal dry unlit tagged CAMPFIRE state. `dowse` also notifies its BE and plays game events; source shows separate particles/sound and client branch.

**Cooking is its own asynchronous independent BE owner.** `CampfireBlock.useItemOn` delegates actual player's ItemStack to `CampfireBlockEntity.getCookableRecipe`, then `placeFood` (NOT an ordinary BlockItem placement, can interact while unlit). 4 independent item slots, `cookingTime[4]`, `cookingProgress[4]`, recipe cache for `RecipeType.CAMPFIRE_COOKING`. On **LIT** server, `CampfireBlock.getTicker` dispatches `CampfireBlockEntity.cookTick`, on **UNLIT** server **cooldownTick** decrements stored progress by 2; on LIT client **particleTick**. Completed dish is dropped at the **physical block center XYZ**, not local-up offset in comparable source, so an item-pop physics/geometry interaction remains a Phase3/Phase7 implementation decision. Source saves `CookingTimes/CookingTotalTimes` and item stacks and supports DataComponents.CONTAINER; `onRemove` drops stored inputs via Containers. Recipes and custom item components are separate cross-mod writer/renderer considerations.

**Smoke and external campfire detection:** `CampfireBlock.isSmokeyPos(Level,pos)` searches **pos.below(1..5)** for a `BlockTags.CAMPFIRES` LIT state; the narrow `VIRTUAL_FENCE_POST` collision shape may pass smoke through a fence and allow a special next-below check. Other game mechanics call this (e.g. bee smoke calming), so simply rotating campfire renderer/collision will miss the *consumer-side semantic vertical scan*. Distinguish physical support below, combustion above, actual bee interaction and vertical detection from smoke *client visual*, and preserve 5-block bounded scan. `SIGNAL_FIRE` adjusts type/extent of client campfire smoke, driven by real hay block below and external consumer. `CampfireBlock.makeParticles` places smoke WORLD-Y/upward velocities, as does Campfire BE `particleTick` which rotates item-effect offsets using four FACING directions and physical XZ; renderer and mechanics must agree without altering unknown particles globally.
