# Шаблон карточки результатов исследования — Planetary

> **Использовать как шаблон, не как готовый доказанный результат.** Рядом с карточкой-планом каждой фазы или подэтапа должен быть соответствующий итоговый файл, на который можно перейти без истории чата. Сейчас пример полной структуры — [Phase 3 / results](phase-03/results/README.md).

## Блок идентификации

- **Фаза и пакет:** <например, Phase 3D / 3R-5>.
- **Версия:** MC1.21.1 / NeoForge21.1.215 / Java21; branch 2.0.
- **Текущий статус:** PLANNED / RESEARCH SOURCE ONLY / ORIGINAL ABI CI PASS / GAME PASS; отдельно указать **research gate R** и **visual gameplay gate V**.
- **Проверенная ревизия:** actual commit SHA + CI run link; если изменений только в docs, CI нового исходного кода *не было*.
- **Первичные материалы:** docs/research/*.md, TSV owner/method/mod matrices, source classfiles/JUnit, release SHA, exact uploaded/action artifact hashes; давать рабочие относительные ссылки, не переносить 30 страниц исследования в итог.

## 1. Что действительно установлено

По владельцу механизма, вызовам/виртуальному dispatch, родительским классам/вызовам-соседям, physical vs local vs camera frame, lifecycle/mod hooks. Все числа указывать с областью измерения: зарегистрированные *ванильные* ID, выбранные original classfiles, отмеченные method call sites, а не все реальные mod JAR или исполняемые в игре ветки.

## 2. Согласованные архитектурные выводы

Где должен быть общий фикс и где он опасен; уже отклонённые подходы и почему, включая «не чинить отдельный блок вместо общего алгоритма», «не переписывать физическую систему XYZ глобально» и «не вращать все вызовы BER/PoseStack». Контракт fallback/noPlanet и custom mods.

## 3. Нерешённые вопросы / acceptance gate

Что осталось SOURCE ONLY, TARGET JVM ONLY, CODE/UNIT TEST ONLY, CLIENT MIXIN PENDING, GAME PENDING, MOD LOADED PENDING. Указывать шесть локальных граней, 12 рёбер, 8 углов, baseline +Y/noPlanet и применимые контексты GUI/виртуальных миров; не отмечать PASS без реальных evidence. Разделять R и V.

## 4. Следующий пакет и карта ссылок

Куда перейти в планах фазы, PHASE3_OWNER_COVERAGE или аналогичном ledger; какой следующий 4/4 research пакет, исходные тесты/CI и где актуальный SESSION_HANDOFF. После каждого 4/4 research или code пакета **обновлять карточку результатов + существующий detailed исследовательский файл/матрицу + план фазы + handoff**, до перехода к следующему «кк».

**Нельзя:** стирать прошлые факты при пересмотре; выдавать JUnit/ASM за интеграционные/игровые тесты; считать любые 3R-5/6/7 закрытыми без реального коммита и верного GitHub CI; превращать шаблон или index в новый самостоятельный источник непроверенных утверждений.
